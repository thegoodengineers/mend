New domains.

Mend repaired itself on Python bugs. Then we gave both workers bugs in chip designs and circuit schematics they had never seen.

Nothing here was shown to the supervisor or used in a self-repair round. The "hardware" is checked in simulation, as chip and board designers check designs before manufacturing.

Real hardware output

Every design exports as Verilog, the language chip toolchains take. This is the PWM generator, emitted by Amaranth through Yosys (hardware/verilog).

(* generator = "Amaranth" *)
module pwm(clk, rst, out, duty);
  reg \$auto$verilog_backend.cc:2355:dump_module$1  = 0;
  wire \$1 ;
  wire [3:0] \$2 ;
  reg [2:0] \$3 ;
  input clk;
  wire clk;
  input [3:0] duty;
  wire [3:0] duty;
  output out;
  wire out;
  reg [2:0] phase = 3'h0;
  input rst;
  wire rst;
  assign \$1  = phase == 3'h7;
  assign \$2  = phase + 1'h1;
  assign out = phase < duty;
  always @(posedge clk)
    phase <= \$3 ;
  always @* begin
    if (\$auto$verilog_backend.cc:2355:dump_module$1 ) begin end
    (* full_case = 32'd1 *)
    if (\$1 ) begin
      \$3  = 3'h0;
    end else begin
      \$3  = \$2 [2:0];
    end
    if (rst) begin
      \$3  = 3'h0;
    end
  end
endmodule

The planted bugs

BugWhat it isBug report the agent got
HW01counter overshoots modulusA mod-10 ModCounter shows 10 before going back to 0, and its wrap pulse comes one cycle late. A mod-4 counter never raises wrap at all.
HW02gray decode wrong above 3GrayToBin gives the wrong number for most codes above 3: converting a value to Gray code and back does not return the original value.
HW03ALU subtracts the wrong way roundThe ALU's SUB operation returns 249 for 10 - 3 and raises the borrow flag.
HW04ALU carry flag wrongThe ALU raises carry on 100 + 50 even though the sum fits in 8 bits, and misses the carry on 200 + 100.
HW05FIFO full one entry earlyA 4-entry SyncFIFO reports full after only 3 writes and drops the 4th write.
HW06UART bytes arrive bit-reversedBytes sent through UartTx arrive bit-reversed at the receiver: sending 0x01 is received as 0x80, and 0xA5 stays 0xA5.
HW07PWM glitch at duty 0With duty set to 0 the PWM output still goes high for one cycle every period, and duty 3 gives 4 high cycles.
HW08debouncer lets bounces throughA bouncing button eventually registers as pressed with Debouncer(4), even though the input never stays high for 4 cycles in a row.
HW09CRC-8 check value wrongCrc8Byte does not produce the standard CRC-8 check value: chaining the bytes of b"123456789" from 0 should give 0xF4.

A whole board · one netlist, shared power rails

A sensor board, brought up in simulation.

USB 5 V in, an LM317-style regulator set to 3.3 V, an NTC temperature sensor with an op-amp buffer and a 1 kHz anti-aliasing filter into the microcontroller's ADC, a reset circuit, power and status LEDs, and I²C pull-ups. 11 bring-up checks, the ones an engineer runs on a new board: is the rail 3.3 V, are the LEDs safe, does the sensor read right, is anything over the MCU's 3.6 V limit.

Hover or tap a part Each part shows what it does, the bring-up check that covers it, and the bug planted in it.

The drawing is illustrative; the circuit is board.cir, checked by test_board.py.

6, 7 → 8, 8 of 8 solved.

Where the gap comes from: the original worker refused BD01 (both runs) and BD02 (one run) in a single turn, replying that a sensor-board report is "a hardware issue, not a bug in the Python library", without running a check. Both workers get the same prompt. The repaired worker's learned workflow starts by running the tests, so it engaged and fixed all 8.

What this shows, and what it doesn't

The gain is efficiency.

Both workers fix every chip-design and schematic bug, so these sets show no gain in what gets solved. What carried over is how: the self-repaired worker reads less, edits precisely and stops when the tests pass, so it needs far fewer turns and tokens. Two runs per worker; the sets are small; everything is simulated, not built on a physical board.
