## Chosen fix: read_file: return the whole file by default instead of a 200-line page

File: `mend/worker.py`

In mend/worker.py make two changes. (1) Change the read_file handler signature from `lines: int = 200` to `lines: int | None = None`. When `lines` is None, return every line from `start` to the end of the file: `chunk = text[start - 1:] if lines is None else text[start - 1 : start - 1 + lines]`. Keep the existing '... (N more lines; file has M lines total)' trailer; it can then only appear when the caller passed an explicit `lines`. (2) Update the read_file entry in TOOLS so its description says: 'Read a text file. By default returns the WHOLE file (from `start` to the end) as numbered lines; pass `lines` only if you deliberately want a smaller window. Each line is prefixed with its number and a TAB; the code starts right after the TAB. To read several files, request them all in one turn.' Leave the input_schema properties unchanged; `lines` stays optional with minimum 1. Do not change any other tool or the loop.

Why it is general: Any long source file currently costs a wasted turn: the worker reads page one, sees the truncation note, then requests page two. Returning complete files by default removes that round trip for every task whose relevant code sits past the first page, whatever the module or bug. The library's files are small, so the extra input tokens are far fewer than the tokens re-sent with a whole additional LLM turn.

## Proposed neatlogs regression guard

`Mend: read_file returned a truncated page`: regex `\.\.\. \(\d+ more lines; file has \d+ lines total\)` on the output of `read_file` spans. Flags read_file calls whose output was cut off before the end of the file. This usually forces the worker to spend an extra turn reading the next page.
