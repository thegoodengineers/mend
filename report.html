## Chosen fix: Add a targeted edit_file (exact string replace) tool and steer edits away from whole-file rewrites

File: `mend/worker.py`

1) Add a new tool to TOOLS named "edit_file". Description: "Edit a file by replacing one exact occurrence of `old` with `new`. `old` must match the file's current text exactly (including indentation; do not include the line-number prefixes shown by read_file) and must occur exactly once - include enough surrounding lines to make it unique. Prefer this over write_file for any change to an existing file." The input_schema is an object with required string properties `path`, `old` and `new`, plus additionalProperties false.
2) Implement it as `@neatlogs.span(kind="TOOL", tool_name="edit_file") def edit_file(work, path, old, new)`. It should:
- resolve the path with _safe_path;
- refuse paths under tests, the same way write_file does;
- read the text;
- count = text.count(old); if count == 0 raise ValueError("`old` not found in file; re-read the exact lines and copy them verbatim"); if count > 1 raise ValueError(f"`old` occurs {count} times; include more surrounding context");
- write text.replace(old, new, 1);
- return f"edited {path}: replaced {old.count(chr(10))+1} line(s) with {new.count(chr(10))+1} line(s)".
Register it in HANDLERS.
3) Change write_file's tool description to: "Create a new file or replace the WHOLE content of a file. Anything you omit is deleted. To change part of an existing file use edit_file instead."
4) In read_file, when the returned chunk ends before the end of the file, append a final line: f"... ({len(text) - (start - 1 + len(chunk))} more lines; file has {len(text)} lines total)". This makes partial reads visible.

Why it is general: The dominant cost across these traces is that the only way to change code is to regenerate a whole file. That silently truncates any file longer than what the model has read (task 23 failed, task 24 nearly failed) and makes even successful one-line fixes slow (task 22). ## Chosen fix: edit_file: on a miss, show the exact current text of a whitespace-insensitive match; make the read_file prefix unambiguous

File: `mend/worker.py`

1) In read_file, change the line-number prefix so it cannot be confused with indentation. Use a tab separator: f"{start + i}\t{line}" instead of f"{start + i}: {line}". Update the edit_file description to say 'do not include the line-number-and-TAB prefix'.

2) In edit_file, when count == 0, try a fallback before raising.
- Split `old` into lines and strip trailing newlines. Compare each line with .strip() against every same-length window of consecutive lines in the file (also stripped).
- If exactly one window matches, apply the edit to that window, but only if every line of `old` differs from the file only in leading or trailing whitespace. To do this:
  - Compute the indentation delta between the first non-blank line of `old` and the first non-blank line of the window.
  - Re-indent every line of `new` by that same delta: add spaces if the file is more indented, remove up to that many leading spaces if it is less.
  - Replace the window lines with the re-indented `new` lines and write the file.
  - Return f"edited {path}: replaced N line(s) with M line(s) (note: your `old` had different indentation than the file; matched ignoring whitespace and re-indented `new` by {delta:+d} spaces)".

- If none match, find the file line most similar to the first non-blank line of `old` using difflib.get_close_matches on stripped lines. Raise ValueError("`old` not found. Closest line in the file is line {n}: {repr(actual_line)} (leading spaces: {k}); your first line was {repr(old_first_line)} (leading spaces: {j}). Copy the text exactly as shown.").

Why it is general: Exact-match string editing is the worker's only way to change existing code. Matching while ignoring whitespace, with re-indentation, plus a precise diagnostic, removes this failure mode for every bug in every file. An unambiguous read prefix stops the mistake at its source.
